# Versioning Policy

This repository uses Semantic Versioning 2.0.0 for public releases.

## Source Of Truth

- The current application version is stored in the root `VERSION` file.
- `VERSION` contains the version only, without a leading `v`.
- The Makefile injects `VERSION` into the build as `APP_VERSION`.
- Git release tags use the same version with a leading `v`, for example
  `v0.1.0`.

## Version Numbers

Use `MAJOR.MINOR.PATCH`:

- Increment `MAJOR` for incompatible CLI, file-format, or documented behavior
  changes after `1.0.0`.
- Increment `MINOR` for new commands, options, TUI workflows, supported MIDI
  behavior, or other backward-compatible capabilities.
- Increment `PATCH` for bug fixes, documentation corrections, and internal
  changes that preserve documented behavior.

Until `1.0.0`, the public contract is still settling:

- `MINOR` may include incompatible behavior changes.
- `PATCH` must remain backward-compatible within the current minor line.
- Document any incompatible pre-1.0 change in `CHANGELOG.md`.

## Pre-Releases

Use SemVer pre-release suffixes when a version is not final:

- `-dev` for active development toward the next release.
- `-alpha.N` for incomplete testable snapshots.
- `-beta.N` for feature-complete snapshots that still need validation.
- `-rc.N` for release candidates.

Do not tag `-dev` builds as releases. Release tags should point to final
versions or explicit alpha, beta, or release-candidate snapshots.

## Git Tags

- Release tags are annotated git tags named `vX.Y.Z` or
  `vX.Y.Z-prerelease.N`, matching `VERSION` with a leading `v`.
- Tags must point at the release commit that updates `VERSION` and
  `CHANGELOG.md`.
- Do not move or delete a published release tag. If a release is bad, publish a
  follow-up patch or pre-release tag.
- Do not create tags for `-dev` versions.
- Tag messages should identify the release and summarize verification:

```sh
git tag -a v0.1.0 -m "Release v0.1.0"
```

Push release commits and tags together:

```sh
git push origin main
git push origin v0.1.0
```

Before creating a tag, confirm the built binary reports the same version:

```sh
./midi-capture --version
```

## GitHub Releases

- Every published release tag should have a matching GitHub Release.
- A GitHub Release must not be published until the release tag's
  `Release Check` workflow has passed.
- Final SemVer tags (`vX.Y.Z`) become normal GitHub Releases.
- Alpha, beta, and release-candidate tags become GitHub pre-releases.
- Use GitHub draft releases while writing notes or attaching assets.
- Release titles should use `midi-capture vX.Y.Z`.
- Release notes should start from the matching `CHANGELOG.md` section, then add
  verification evidence and known limitations.
- Use the GitHub "latest release" marker only for the newest stable
  non-prerelease version.
- Attach binary artifacts only when they were built from the tagged commit and
  the build steps are documented. Until packaging is repeatable, source archives
  generated by GitHub are the release artifact of record.

## Regression And CI Gates

- All pull requests and pushes to `main` must pass the `CI` workflow.
- Release tags must pass the `Release Check` workflow before a GitHub Release is
  published.
- `CI` and `Release Check` both run `make clean`, `make`, `make test`, and a
  version smoke test.
- `Release Check` also verifies that the git tag matches `VERSION` and rejects
  `-dev` release tags.
- Configure the GitHub repository to require `CI / Build and regression tests`
  before merging to `main`.
- If GitHub rulesets are available, require `Release Check / Validate release
  tag` before publishing releases from `v*` tags.
- Manual smoke tests remain required for releases that change CLI, playback,
  recording, MIDI device handling, or TUI behavior because CI cannot validate
  real device interaction.

GitHub CLI example for a stable release:

```sh
gh release create v0.1.0 \
  --title "midi-capture v0.1.0" \
  --notes-file release-notes.md \
  --latest
```

GitHub CLI example for a release candidate:

```sh
gh release create v0.2.0-rc.1 \
  --title "midi-capture v0.2.0-rc.1" \
  --notes-file release-notes.md \
  --prerelease \
  --latest=false
```

## Changelog

- Keep user-facing changes in `CHANGELOG.md`.
- Maintain an `Unreleased` section while developing.
- At release time, move relevant entries under `## X.Y.Z - YYYY-MM-DD`.
- Include breaking changes, migration notes, and manual verification gaps when
  they affect users.

## Release Checklist

1. Decide the next version using the rules above.
2. Update `VERSION`.
3. Move `CHANGELOG.md` entries from `Unreleased` into a dated release section.
4. Run `make clean`, `make`, and `make test`.
5. Run the manual smoke tests listed in
   `docs/tui-refactor-sprints/phase-11-final-verification-release.md` when the
   release changes CLI, playback, recording, or TUI behavior.
6. Commit the release changes using the Lore Commit Protocol.
7. Verify `./midi-capture --version` prints the release version.
8. Create an annotated tag named `vX.Y.Z`.
9. Push the release commit and tag to GitHub.
10. Wait for the tag's `Release Check` workflow to pass.
11. Create a GitHub Release from the tag.
12. Bump `VERSION` to the next `-dev` version on the following development
   commit.
